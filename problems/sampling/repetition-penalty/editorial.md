## The idea

Whether a logit gets penalized depends on one boolean question for each `(row, token)`
pair: does this token appear in this row's history? Represent the answers as a boolean
table `seen` of shape `(B, V)`. Each row of `prev_tokens` lists column indices into
`seen`. Converting index lists into a boolean table in one vectorized step is a
**scatter**: start from an all-`False` table and write into `seen[b, prev_tokens[b, t]]`
for every `b` and `t` at once.

Scattering handles both edge cases without extra code:

- **Duplicates.** A token that appears multiple times is written multiple times. Because
  every write stores the same value, the final entry is identical to writing once. Set
  membership falls out automatically without `unique` or occurrence counts.
- **Padding.** Instead of filtering padding out (which would produce ragged rows),
  scatter the boolean mask `prev_tokens != pad_id`. Each padding entry writes `False`
  into the `pad_id` column, which is already `False`. Because all writes to any single
  position agree, the order in which the framework applies them does not matter.

Once `seen` is built, compute the penalized value for every entry from the original
`logits` and select between the penalized and original values using `seen`.

## Reference solution (PyTorch)

```python
def apply_repetition_penalty(logits, prev_tokens, penalty, pad_id):
    seen = torch.zeros_like(logits, dtype=torch.bool).scatter(1, prev_tokens, prev_tokens != pad_id)
    penalized = torch.where(logits > 0, logits / penalty, logits * penalty)
    return torch.where(seen, penalized, logits)
```

In JAX, the scatter is `jnp.zeros(shape, bool).at[rows, prev_tokens].set(...)` with
`rows = jnp.arange(B)[:, None]`. In MLX, it is `mx.put_along_axis(..., axis=1)`.

An equally valid formulation works on the history side instead of the vocabulary side.
Gather the logits at `prev_tokens`, penalize those `(B, T)` values, restore the entries
at padding positions, and scatter the results back into a copy of `logits`. This touches
only $B \cdot T$ entries plus one copy. It handles duplicates for the same reason: every
occurrence of a repeated token receives the same once-penalized value computed from the
original `logits`.

## Why the sign matters

Dividing a positive logit by $\theta > 1$ lowers it. Dividing a negative logit by
$\theta$ moves it closer to zero, which *raises* it (for example,
$-1.0 / 1.25 = -0.8$). To push every seen token toward a lower probability, negative
logits must be multiplied by $\theta$ instead. A logit of `0.0` is unchanged either way,
and `-inf` stays `-inf` under multiplication.

## Common mistakes

- **Always dividing.** The original CTRL paper prints division for all seen logits.
  Division lowers a score only when it is positive. Because logits are negative roughly
  half the time, always dividing rewards repeated tokens with negative logits. Swapping
  the two branches rewards every repeated token.
- **Penalizing padding.** Scattering `True` for every entry marks the `pad_id` column in
  every row that contains padding. Because `pad_id` is a real vocabulary entry (often the
  end-of-sequence token), short sequences in a batch get a suppressed EOS token.
- **Penalizing per occurrence.** Counting occurrences with `scatter_add`, or updating
  logits in place inside a loop over history positions, applies $\theta^{\text{count}}$.
  The specification depends only on set membership. In-place loops trigger this bug by
  accident when a second occurrence penalizes an already-penalized value.
- **Sharing one seen set across the batch.** Indexing columns with the flattened history
  (`logits[:, prev_tokens.flatten()]`) penalizes every row for tokens generated by any
  other row.
- **Looping in Python over rows or tokens.** A Python loop can produce the right values
  but runs one to two orders of magnitude slower because each iteration pays tens of
  microseconds of interpreter and kernel-dispatch overhead. In the speed test, a loop
  over rows is roughly 100x slower, and a loop over tokens is even slower.

## Complexity

This approach takes $O(B \cdot (T + V))$ time and $O(B \cdot V)$ extra memory for the
boolean mask and output tensor. A one-hot comparison like
`prev_tokens[:, :, None] == arange(V)` is also loop-free, but it materializes a
`(B, T, V)` intermediate in $O(B \cdot T \cdot V)$ time and memory. That works for small
shapes and becomes impractical at real vocabulary sizes ($V \approx 10^5$).

## In the wild

The penalty comes from Keskar et al., "CTRL: A Conditional Transformer Language Model
for Controllable Generation" (2019), which samples from
$p_i \propto \exp\!\big(x_i / (T \cdot I(i \in g))\big)$, where $T$ is temperature and
$I(i \in g) = \theta$ for tokens in the generated history $g$ (1 otherwise), suggesting
$\theta \approx 1.2$. Hugging Face's
`RepetitionPenaltyLogitsProcessor` implements the sign-aware rule from this problem
using the gather, `where`, and scatter formulation. Both llama.cpp's `repeat_penalty`
and vLLM's `repetition_penalty` apply the same rule. Engines differ in what counts as
history (Hugging Face includes the prompt, while llama.cpp uses a window of the last
`repeat_last_n` tokens), so the same penalty value can behave differently across them.
The frequency and presence penalties in OpenAI-style APIs are additive relatives that
subtract from logits, and the frequency penalty intentionally scales with occurrence
count.
