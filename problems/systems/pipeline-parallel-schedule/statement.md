A model too large for one device is cut into consecutive blocks of layers, one
block per device, and an activation travels from device to device (the placement
`device-map-solver` computes). Run by itself, a sequence keeps one device busy at a
time and leaves the rest idle. With several sequences in flight the stages can work
on different sequences at once. Write the scheduler that makes them: it decides,
at every instant, which waiting token each free stage computes next, under rules
exact enough that the whole timeline is determined.

## Specification

```python
async def run_pipeline(pipe, requests: list[tuple[str, int, int]]) -> dict[str, list[int]]: ...
```

**Time** is the event loop's clock, and one unit is one millisecond:
`asyncio.sleep(3)` waits 3 ms. The clock reads 0 when `run_pipeline` is called.
All durations and arrival times are integers. Use `asyncio` only, never the real
clock.

**The requests.** Each request is a tuple `(seq_id, arrival_ms, n_tokens)`: a
sequence with a unique id that arrives at `arrival_ms` and needs `n_tokens`
$\ge 1$ tokens generated. The list is sorted by arrival time, and a request's
position in the list is its **request index**.

**The pipeline.** `pipe` has $S$ = `pipe.n_stages` stages, numbered in the order the
layers run. To generate token $t$ of a sequence, every stage $0, \dots, S-1$ must
process it, in order. The **job** $(s, t)$ is token $t$ of sequence $s$.

- `await pipe.run(stage, seq_id, token)` makes `stage` compute that job. It takes
  `pipe.service_ms[stage]` ms (a positive integer). At the last stage it returns the
  generated token id (an int); at every other stage it returns `None`.
- `await pipe.transfer(stage, seq_id, token)` moves the output of `stage` for that
  job to the device of `stage + 1`. It takes `pipe.transfer_ms[stage]` ms (a
  positive integer; the tuple has $S - 1$ entries). Any number of transfers can be
  under way at once.

The hardware has four **physical rules**. A call that breaks one raises
`PipelineError`:

1. A stage computes one job at a time: `run` may start only when the stage's
   previous `run` is finished.
2. Stage $i > 0$ may start a job only when that job's transfer from stage $i - 1$
   is finished; a transfer may start only when stage $i - 1$ has finished the job.
3. Stage 0 may start token 0 of a sequence only at or after its arrival time.
4. Stage 0 may start token $t > 0$ of a sequence only when token $t - 1$ has
   finished the **last** stage: the model reads its own previous token. (Carrying
   that token id back to the first device takes no time.)

An operation that starts at time $T$ and takes $\delta$ is *finished* at
$T + \delta$, and whatever waits for it may start at exactly $T + \delta$. The
rules are checked against these times, not against which `await` has returned.

**The schedule.** `run_pipeline` must produce exactly this schedule:

- A job's **ready time** at a stage is the earliest moment rules 2 to 4 allow it
  to start there. For stage 0 that is the arrival time (token 0) or the moment the
  previous token finished the last stage. For stage $i > 0$ it is the moment its
  transfer finished, and **the transfer starts the instant stage $i - 1$ finishes
  the job**, so the ready time is that finish time plus `transfer_ms[i - 1]`.
- **No stage idles while a job is ready for it.** Whenever a stage is free and at
  least one job is ready for it (ready time $\le$ now), it starts one at once.
- **Which one:** the job with the earliest ready time; among jobs with the same
  ready time, the one whose request index is smaller.

A decision at time $T$ takes into account everything that happens at $T$: a job
that becomes ready at $T$ competes for a stage that becomes free at $T$, and with
every other job that becomes ready at $T$, whatever order your code learns of
these events in.

**The result.** `run_pipeline` returns when every token has finished the last
stage, with a dict that maps each `seq_id` to the list of its token ids (the values
returned by the last stage) in token order.

## Example

Two stages with `service_ms = (2, 3)` and `transfer_ms = (1,)`, and
`requests = [("a", 0, 2), ("b", 0, 2), ("c", 4, 1)]`. Jobs are written `a[0]`:

| time | stage 0 | stage 1 | notes |
|---|---|---|---|
| 0 | starts `a[0]` | | `a[0]` and `b[0]` are both ready at 0; `a` is the earlier request |
| 2 | starts `b[0]` | | `a[0]` leaves for stage 1, arrives at 3 |
| 3 | | starts `a[0]` | |
| 4 | starts `c[0]` | | `c` arrives as the stage becomes free; `b[0]` arrives at stage 1 at 5 and waits |
| 6 | starts `a[1]` | starts `b[0]` | `a[0]` is done, so `a[1]` is ready at 6, when stage 0 becomes free |
| 9 | starts `b[1]` | starts `c[0]` | `c[0]` has been ready since 7, `a[1]` only since 9 |
| 12 | | starts `a[1]` | `b[1]` arrives at 12 as well, but `a[1]` has been ready since 9 |
| 15 | | starts `b[1]` | |
| 18 | | | done |

All five tokens are generated by 18 ms. With one token in the pipeline at a time,
each token takes $2 + 1 + 3 = 6$ ms and the five take 30 ms.

A tie decided by request index: `service_ms = (2, 2)`, `transfer_ms = (1,)`,
`requests = [("a", 0, 2), ("b", 5, 1)]`. `a[0]` runs on stage 0 until 2 and on
stage 1 from 3 to 5. At time 5 two jobs become ready for stage 0 at once: `a[1]`,
because its previous token has just left the last stage, and `b[0]`, because `b`
arrives. `a` has the smaller request index, so stage 0 starts `a[1]` at 5 and
`b[0]` at 7.

## Constraints

- $1 \le S \le 8$; service and transfer times are integers from 1 to 20; at most
  16 requests of at most 40 tokens; arrival times are integers $\ge 0$. All times
  are therefore exact.
- The test records the start time of every `run` and `transfer` and compares the
  set of `(time, stage, sequence, token)` starts with the schedule defined above,
  which is unique. The returned token lists are compared exactly.
- The time at which `run_pipeline` returns (the makespan) must equal that
  schedule's. One public case also checks it against a bound that does not depend
  on the reference: with eight sequences of 30 tokens on four stages, the
  throughput must be within 5 percent of the bottleneck stage's rate, that is,
  the makespan at most `240 * max(service_ms) / 0.95` ms.
- A `PipelineError` fails the case, whether or not the solution catches it.

## Why this matters

Pipeline parallelism is how a model is spread over devices when tensor parallelism
is not an option: across nodes without a fast interconnect (vLLM's
`--pipeline-parallel-size` for multi-node serving), across unequal GPUs, or across
GPU and CPU with a device map. Its weakness is plain in the single-sequence
timeline: every device waits for all the others, so $S$ devices give the speed of
one. The capacity only comes back when the stages are kept busy with *different*
sequences, and what limits it then is the slowest stage, not the sum of all of
them. A scheduler that lets one sequence hold the pipeline, starts a transfer
late, or leaves a stage idle while an activation sits ready in front of it gives
away exactly the throughput the extra devices were bought for.
