Implement greedy autoregressive generation for a batch of prompts with different lengths, using a single model call per decoding step. Pad shorter prompts so the batch forms a rectangle, ensure padding has zero effect on any row's predictions, stop each row at its own end-of-sequence (EOS) token, and exit the loop as soon as all rows finish.

## Specification

```python
def batch_generate(model, prompts, max_new_tokens, eos_id): ...
```

`model` is an [`MLXTinyLM`](../../../python/src/learnai/kit/mlxlm.py), the kit's small seeded transformer in `mlx.nn`. On a batch of $B$ rows and $T_{\text{call}} \ge 1$ tokens per row, it accepts an optional cache along with explicit attention masks and token positions:

```python
logits, cache = model(tokens, mask=mask, positions=positions)          # prompt pass
logits, cache = model(tokens, cache, mask=mask, positions=positions)   # decode step
```

- `mask` is an additive float32 array that replaces the model's built-in causal mask before softmax. It must broadcast to `(B, 1, T_call, C + T_call)`, where $C$ is the number of key columns already stored in `cache` ($C = 0$ on the first call). Entry `[b, 0, i, j]` is `0` if query $i$ of row $b$ may attend to key column $j$, and `-inf` otherwise. Key columns are ordered across calls with cached columns first, followed by the columns of the current call.
- `positions` provides the integer position of each token in `tokens`, used by RoPE or by the sinusoidal embedding when `rope=False`.
- `logits[b, -1]` gives the next-token logits for row `b`. `cache` holds all `B` rows, and every subsequent call using `cache` must pass the same batch size `B`. Both `logits` and `cache` are lazy, and the model never mutates an existing cache.

**Target output:** Let $\operatorname{solo}(p)$ denote greedy decoding of a single prompt $p$ alone, using positions $0, 1, 2, \dots$, a standard causal mask, and taking the argmax of the next-token logits at each step. Row $b$ of the returned list must match the tokens generated by $\operatorname{solo}(\texttt{prompts}[b])$ until row $b$ is *finished*, meaning either:

- it has generated `eos_id` (the EOS token is included as the last element of row $b$), or
- it has generated `max_new_tokens` tokens.

**Arguments and return value:**

- `prompts`: list of $B \ge 1$ lists of token ids with lengths $L_b \ge 1$. Do not modify the input lists.
- `max_new_tokens`: Python int $\ge 1$, the generation limit for each row.
- `eos_id`: Python int or `None`. Only generated tokens trigger stopping, so an `eos_id` inside a prompt is treated as a normal token. If `eos_id` is `None`, every row generates `max_new_tokens` tokens.
- Returns a list of $B$ lists of Python ints containing only the generated tokens (excluding the prompts). Row $b$ has length $g_b$ with $1 \le g_b \le \texttt{max\_new\_tokens}$.

**Batching protocol:** Let $T = \max_b L_b$ be the padded prompt width, $P_b = T - L_b$ be the number of padding slots for row $b$, and $g_{\max} = \max_b g_b$ be the longest generation length.

1. **Left-pad the prompts.** Build a single `(B, T)` batch where row $b$ begins with $P_b$ padding slots followed by `prompts[b]`. Determine which positions are padding strictly from the prompt lengths, never by checking token values. Any token id may fill padding slots, and that same id may appear as a real token in a prompt.
2. **Mask out padding.** On the prompt call, a real query at column $i \ge P_b$ may attend to key column $j$ if and only if $P_b \le j \le i$. No real query in row $b$ may attend to any padding column of row $b$ during the prompt call or any later decode call.
3. **Keep padding queries finite.** A query whose entire mask row is `-inf` produces `0 / 0 = NaN` in softmax. In the next transformer layer, that NaN becomes a key value, and `NaN + (-inf)` remains `NaN`, bypassing the additive mask and corrupting every row that masks it. Allow each padding query to attend to itself so its output stays finite.
4. **Shift positions per row.** Assign the real token at column $j$ of row $b$ position $j - P_b$ so every prompt starts at position 0, matching its solo run. Padding slots may have any valid non-negative integer positions.
5. **Decode one token per step.** After the prompt call, call the model with shape `(B, 1)` and `cache`. For the $s$-th generated token ($s \ge 1$), feed each running row its newly generated token at position $L_b + s - 1$, allowing it to attend to every cached and current column except its own padding columns. Feed finished rows any filler token, ignore their logits, and do not append to them.
6. **Stop promptly.** Exit the loop as soon as every row is finished. The model is called exactly $g_{\max}$ times, so the final token of the longest row is never fed back into the model.

**Evaluation rules (`EvalSpy`):**

- Call `mx.eval` at most once per step (at most $g_{\max}$ times total). Do not use `mx.async_eval`.
- Read from the device at most once per step (at most $g_{\max}$ times total). Use a single `.tolist()` or `np.array` call on the whole batch of tokens rather than calling `.item()` per row.

**Cost limits:**

- `model.counters.forward_calls` $\le g_{\max}$.
- `model.counters.tokens_processed` $\le B \cdot T + B \cdot (g_{\max} - 1)$.

## Shapes

| name | shape | dtype |
|---|---|---|
| `prompts` | list of $B$ lists of $L_b$ ints | Python `int` |
| `tokens` (to `model`) | `(B, T)`, then `(B, 1)` | integer |
| `mask` (to `model`) | broadcastable to `(B, 1, T_call, C + T_call)` | float32 |
| `positions` (to `model`) | `(B, T)`, then `(B, 1)` | integer |
| `logits` (from `model`) | `(B, T_call, vocab_size)` | float32 |
| result | list of $B$ lists of $g_b$ ints | Python `int` |

## Example

```python
model = MLXTinyLM(seed=1)  # vocab_size 64
prompts = [[5, 17, 42, 9, 3], [8, 1], [30, 31, 32]]

batch_generate(model, prompts, max_new_tokens=6, eos_id=1)
# [[46, 30, 1],
#  [30, 34, 36, 44, 8, 43],
#  [58, 41, 51, 60, 6, 56]]
```

Here $T = 5$ and the padding counts are $P = (0, 3, 2)$. Using `.` to represent a padding slot, the prompt call passes:

```
tokens                    positions
[[ 5, 17, 42,  9,  3],    [[0, 1, 2, 3, 4],
 [ .,  .,  .,  8,  1],     [., ., ., 0, 1],
 [ .,  ., 30, 31, 32]]     [., ., 0, 1, 2]]
```

Taking the argmax of `logits[:, -1]` yields the first generated tokens `[46, 30, 58]`. The second call passes `[[46], [30], [58]]` at positions `[[5], [2], [3]]` with a mask of shape `(3, 1, 1, 6)` that places `-inf` on columns 0 to 2 of row 1 and on columns 0 and 1 of row 2.

Row 0 generates EOS token `1` on step 3 and finishes as `[46, 30, 1]`. Rows 1 and 2 never generate `1` and run for all 6 steps. Notice that the `1` at the end of prompt `[8, 1]` does not stop row 1 because it belongs to the prompt. Overall $g_{\max} = 6$, resulting in 6 model calls, 6 evaluations, 6 device reads, and $3 \cdot 5 + 3 \cdot 5 = 30$ tokens processed. During the final three steps, row 0 receives a filler token.

## Constraints

- $1 \le B \le 8$, $1 \le L_b \le 24$, and $1 \le \texttt{max\_new\_tokens} \le 20$.
- Generated tokens are compared for exact equality against $\operatorname{solo}$ run without batching or caching. The test models keep the top two logits separated by more than `1e-3` at every step, well above the ~`1e-6` numerical difference between batched and single-row passes. If two logits were ever tied, argmax picks the lower token id.
- Tests cover both RoPE models and absolute sinusoidal position models (`rope=False`), with two or three layers.
- Evaluation rules and cost limits are enforced as exact counts. A solution that returns the right tokens while exceeding any count fails.

## Why this matters

Batching turns idle GPU compute into throughput. On this machine, running 32 prompts through a small transformer takes 0.16 s in a single batch compared to 4.3 s one by one. Because real requests have unequal lengths, every batched inference engine relies on padding, and padding is where batched outputs quietly diverge from single-request outputs.

These bugs fail in subtle ways. Right-padding or failing to mask padding alters every short row's tokens. Applying the padding mask during prefill but omitting it during decode gets the first token right and drifts afterward. Leaving a padding query completely masked produces NaNs that propagate across layers and corrupt the entire batch, which is why both `mlx-lm` and Hugging Face `transformers` explicitly guard against fully masked rows. Finally, finished rows must stop emitting output while keeping their slots in the batch rectangle, because shrinking the batch mid-loop would invalidate every array shape in the KV cache.
